# 多产品统一 UI 设计规范

**Multi-Product UI Design Specification**

版本：V1.0\
状态：初稿\
适用范围：Web、Windows、macOS、iOS、Android\
参考体系：Apple HIG、Google Material Design、Microsoft Fluent
2、Atlassian Design System

------------------------------------------------------------------------

# 1. 设计目标与基本原则

## 1.1 设计目标

建立一套跨产品、跨页面、跨平台的统一 UI
设计体系，使不同产品在保持自身业务特点的同时，拥有一致的视觉语言、交互行为和组件使用规范。

设计规范不以模仿某个品牌的视觉风格为目标，而是建立明确的设计决策标准。

核心目标：

1.  一致性：相同功能在不同产品中采用一致的交互逻辑。
2.  清晰性：页面信息层级明确，用户能够快速识别核心内容和主要操作。
3.  可预测性：组件行为符合用户预期，避免同一控件在不同页面表现不一致。
4.  可复用性：建立统一的基础组件和设计 Token。
5.  可扩展性：允许不同产品根据业务需求扩展组件，而不破坏基础规范。
6.  可访问性：保证不同使用环境和能力条件下的可用性。

## 1.2 核心设计原则

### Hierarchy（层级）

明确页面中信息、内容和操作的优先级。

-   核心内容优先呈现。
-   主要操作应具有足够的视觉强调。
-   次要信息通过字号、颜色、间距进行弱化。
-   避免所有元素使用相同的视觉权重。

### Harmony（协调）

界面中的颜色、字体、间距、圆角、图标和组件应形成统一的视觉体系。

-   避免无意义的装饰。
-   避免过多边框和阴影。
-   保持组件之间的视觉协调。
-   使用统一的间距和尺寸体系。

### Consistency（一致性）

相同语义的组件应保持相同的行为和视觉表现。

-   相同功能使用相同组件。
-   相同操作使用相同的交互反馈。
-   相同状态使用相同的视觉表达。
-   不允许在不同页面中随意改变组件含义。

# 2. 设计系统架构

整个设计系统分为四个层级。

  层级   名称                   职责
  ------ ---------------------- --------------------
  L1     Foundations            基础设计规范
  L2     Design Tokens          设计变量与统一参数
  L3     Components             基础组件和复合组件
  L4     Patterns & Templates   页面模式和业务模板

## 2.1 Foundations

定义整个产品体系的基础设计语言：

-   颜色系统
-   字体系统
-   间距系统
-   尺寸系统
-   圆角系统
-   阴影与层级
-   图标系统
-   动效系统
-   可访问性规则

## 2.2 Design Tokens

所有基础设计参数必须通过 Token 管理，不允许在不同页面中随意定义。

Token 至少分为三个层级：

**Primitive Tokens**

基础原始变量，例如：

-   `color.blue.500`
-   `color.gray.100`
-   `spacing.4`
-   `radius.8`

**Semantic Tokens**

具有明确语义的变量，例如：

-   `color.background.primary`
-   `color.text.primary`
-   `color.text.secondary`
-   `color.border.default`
-   `color.action.primary`
-   `color.status.danger`

**Component Tokens**

组件专用变量，例如：

-   `button.height.medium`
-   `button.radius`
-   `input.border.focus`
-   `menu.item.height`
-   `dialog.width.medium`

组件 Token 应优先引用 Semantic Tokens，而不是直接引用颜色等原始变量。

## 2.3 Components

所有重复使用的 UI 元素必须优先使用统一组件库。

组件分为：

-   基础组件：Button、Input、Checkbox、Radio、Switch。
-   选择组件：Select、Dropdown、Combobox、Pop-up Button。
-   导航组件：Tabs、Breadcrumb、Navigation。
-   操作组件：Menu、Context Menu、Toolbar。
-   展示组件：Card、List、Table、Badge。
-   反馈组件：Dialog、Alert、Toast、Tooltip。
-   布局组件：Sidebar、Header、Panel、Container。

## 2.4 Patterns & Templates

将基础组件组合成经过验证的业务界面模式。

例如：

-   设置页面
-   设备管理页面
-   数据列表页面
-   编辑器页面
-   详情页面
-   表单页面
-   仪表盘页面

不同产品可以有不同的页面模板，但应共享相同的基础组件和设计 Token。

# 3. 视觉基础规范

## 3.1 颜色系统

采用语义化颜色体系，不允许仅通过颜色名称定义组件用途。

  Token                  用途
  ---------------------- ----------------
  Background Primary     页面主背景
  Background Secondary   次级区域背景
  Surface                卡片及浮层背景
  Text Primary           主要文本
  Text Secondary         辅助文本
  Text Disabled          禁用文本
  Border Default         默认边框
  Border Strong          强调边框
  Action Primary         主要操作
  Action Secondary       次要操作
  Status Success         成功状态
  Status Warning         警告状态
  Status Danger          危险状态
  Status Info            信息状态

设计要求：

1.  颜色必须具有明确的语义。
2.  不允许仅通过颜色区分操作状态，还应结合图标、文本或形态。
3.  危险操作使用统一的危险色。
4.  Disabled 状态应明显区别于正常状态。
5.  支持 Light / Dark 两套主题。
6.  不同产品可以拥有品牌强调色，但不得随意改变状态色的语义。

具体色值应在视觉基线确定后统一定义，不在业务页面中自行创造颜色。

## 3.2 字体系统

字体应采用统一的层级体系。

  Token        使用场景
  ------------ --------------------
  Display      大型展示标题
  Heading 1    页面主标题
  Heading 2    一级区块标题
  Heading 3    二级区块标题
  Body Large   重要正文
  Body         普通正文
  Body Small   辅助正文
  Caption      注释、辅助说明
  Label        表单标签、按钮标签

要求：

-   标题与正文具有清晰的层级差异。
-   避免过多字体粗细和字号。
-   数值、时间、设备参数等内容应考虑等宽数字的对齐需求。
-   中英文混排应保证字重和视觉高度协调。
-   优先使用系统字体或项目统一指定的字体。

## 3.3 间距系统

采用统一的 4pt 基础间距体系。

  Token        数值 典型用途
  ---------- ------ --------------
  Space 1         4 图标与文字
  Space 2         8 紧密元素
  Space 3        12 表单内部
  Space 4        16 组件内部
  Space 5        20 小型区块
  Space 6        24 区块间距
  Space 8        32 大区块
  Space 12       48 页面分区
  Space 16       64 大型布局间距

要求：

-   相同层级的组件使用一致间距。
-   内容分组之间的间距应大于组内间距。
-   不允许为了填满空间而随意添加间距。
-   不同屏幕尺寸下可以使用响应式间距，但应保持 Token 体系。

## 3.4 圆角系统

建立统一圆角 Token：

-   Radius XS：4
-   Radius SM：6
-   Radius MD：8
-   Radius LG：12
-   Radius XL：16
-   Radius Full：9999

不同类型的组件应采用固定圆角规范。

例如：

-   输入框：SM 或 MD。
-   按钮：SM 或 MD。
-   卡片：LG。
-   弹窗：LG 或 XL。
-   圆形图标按钮：Full。

避免在同一页面中出现大量不同圆角。

## 3.5 阴影与层级

界面层级应优先通过背景、间距和边界区分，而不是依赖大量阴影。

建议定义：

-   Elevation 0：普通页面。
-   Elevation 1：卡片及轻微浮层。
-   Elevation 2：菜单及弹出面板。
-   Elevation 3：Dialog。
-   Elevation 4：最高层级的临时交互界面。

阴影应保持克制，并确保 Light / Dark 模式下均有足够的层级辨识度。

# 4. 页面布局规范

## 4.1 页面信息层级

页面应当具有清晰的三级信息结构：

**一级：核心信息**

-   页面标题。
-   当前页面主要任务。
-   核心数据或主要内容。
-   最重要的操作入口。

**二级：辅助信息**

-   内容说明。
-   分类和筛选。
-   状态信息。
-   相关数据。

**三级：次级信息**

-   更多操作。
-   帮助说明。
-   辅助参数。
-   不常用功能。

不允许所有信息同时使用最高视觉强调。

## 4.2 页面区域划分

复杂工具型应用建议采用以下结构：

1.  Application Header：应用顶部区域。
2.  Navigation：导航区域。
3.  Main Content：主要内容区域。
4.  Inspector / Sidebar：属性或辅助信息区域。
5.  Action Area：与当前任务相关的操作区域。

各区域职责必须明确，不应出现同一功能在多个区域重复提供且行为不一致的情况。

## 4.3 内容组织

页面布局应服务于用户任务，而不是简单堆叠卡片。

要求：

-   一个区块应有明确的业务目的。
-   相关信息应归为同一组。
-   操作应尽量靠近其作用对象。
-   次级信息应适当折叠或弱化。
-   长内容应使用明确的分组和层级。

## 4.4 多产品一致性

不同产品可以使用不同的页面结构，但必须遵守：

-   基础字体体系一致。
-   颜色语义一致。
-   基础组件行为一致。
-   交互反馈一致。
-   Token 命名和组件 API 一致。

允许扩展业务组件，不允许重复创建含义相同但行为不同的基础组件。

# 5. 按钮设计规范

## 5.1 按钮分类

按钮必须首先根据操作语义分类，再决定视觉样式。

  类型            作用                         使用场景
  --------------- ---------------------------- ------------------------
  Primary         当前区域最重要的操作         保存、创建、确认
  Secondary       支持性操作                   取消、返回、编辑
  Tertiary        低强调操作                   查看详情、辅助操作
  Destructive     有风险的操作                 删除、清空、重置
  Icon Button     图标形式的局部操作           关闭、搜索、设置
  Toggle Button   切换持续状态                 加粗、对齐、工具模式
  Split Button    一个主要动作加相关附加动作   默认导出及其他导出方式
  Menu Button     打开操作菜单                 更多、新建选项

## 5.2 按钮优先级

-   一个主要操作区域原则上只设置一个 Primary Button。
-   次要操作不得使用与主按钮相同的视觉权重。
-   多个同级次要操作使用中性样式。
-   删除、清空等危险操作应有明确的危险语义。
-   不常用操作优先放入 More Menu。

Primary Button 应当具有足够的对比度和清晰的动作文案。

## 5.3 按钮状态

所有交互按钮必须定义以下状态：

  状态       表现要求
  ---------- --------------------------------
  Default    正常可操作状态
  Hover      鼠标悬停反馈
  Focus      键盘焦点状态
  Pressed    按下状态
  Disabled   不可操作状态
  Loading    操作进行中
  Selected   当前选中状态，适用于切换类按钮

状态变化应保持一致，不允许只通过细微颜色变化表达重要状态。

## 5.4 按钮文案

按钮文案应明确表达动作。

推荐：

-   保存
-   保存更改
-   创建项目
-   删除设备
-   导出视频
-   连接设备

避免：

-   OK
-   Go
-   Click Here
-   确定一下
-   处理

Cancel、Close、Done 等文案应根据实际任务语义使用，不能互相替代。

# 6. 菜单与选择控件规范

本章节重点采用 Apple HIG 的交互语义，并参考 Fluent 2、Material Design
的菜单行为规范。

## 6.1 Menu

定义：一组命令、选项或状态。

使用场景：

-   一组相关操作。
-   一组可切换的状态。
-   当前视图的辅助命令。

要求：

-   菜单必须有明确的触发控件。
-   菜单项应简短、明确。
-   操作型菜单项优先使用动词。
-   菜单内容应根据当前上下文合理启用或禁用。
-   避免多层嵌套，原则上不超过一级子菜单。
-   不应将 Menu 作为主要导航方式。
-   点击菜单项后，应按操作语义关闭菜单或更新选择状态。

## 6.2 Menu Bar Menu

定义：应用级命令集合。

使用场景：

-   File
-   Edit
-   View
-   Window
-   Help

要求：

-   菜单内容作用于整个应用或应用级任务。
-   菜单分类必须具有明确含义。
-   相同功能不得在多个菜单中重复出现。
-   常用操作可以提供键盘快捷键。
-   应用级命令与对象级命令必须区分。

## 6.3 Pop-up Button

定义：用于从多个选项中选择一个值的控件。

典型场景：

-   选择分辨率。
-   选择语言。
-   选择画质。
-   选择字体。
-   选择设备。

要求：

-   默认显示当前选中的值。
-   用户选择后更新当前值。
-   当前选择应具有明确的视觉反馈。
-   支持键盘操作。
-   如果选项需要搜索，应考虑使用 Combobox。

## 6.4 Pull-down Button

定义：用于在特定上下文中触发命令的按钮。

典型场景：

-   导出方式。
-   当前设备操作。
-   图片处理命令。
-   当前项目的附加操作。

要求：

-   按钮本身不表示一个持久选择值。
-   按钮标题应描述操作集合。
-   菜单项应描述实际执行的命令。
-   菜单内容应与当前上下文相关。
-   执行操作后，不应错误地将命令显示为当前选中值。

## 6.5 Context Menu

定义：与当前对象或任务相关的常用动作集合。

典型场景：

-   文件右键菜单。
-   图层右键菜单。
-   画布组件右键菜单。
-   设备列表右键菜单。

要求：

-   菜单内容必须与当前对象相关。
-   不适用的操作应隐藏或禁用。
-   危险操作应与普通操作区分。
-   常用操作优先排列。
-   应支持鼠标、触控板及适用平台的长按交互。
-   不应把应用级命令全部复制到上下文菜单中。

## 6.6 Select / Dropdown / Combobox

这三个概念不能与 Menu 混用。

  --------------------------------------------------------------------------------------------------------
  组件                    定义                                                     使用场景
  ----------------------- -------------------------------------------------------- -----------------------
  Select                  从选项中选择值                                           固定选项

  Dropdown                通常表示展开式选择或操作入口，具体语义需由设计系统定义   简单选项或操作

  Combobox                输入与选项选择相结合                                     可搜索的大型选项集合
  --------------------------------------------------------------------------------------------------------

当用户需要填写或选择信息时，应优先考虑 Select、Dropdown 或
Combobox，而不是将操作菜单当成表单控件。

# 7. 表单与输入控件规范

## 7.1 输入控件

包括：

-   Text Field
-   Text Area
-   Number Input
-   Password Input
-   Search Field
-   Select
-   Checkbox
-   Radio Button
-   Switch
-   Slider

## 7.2 标签与说明

每个输入控件应明确表达：

-   输入项名称。
-   是否必填。
-   输入格式。
-   必要的辅助说明。
-   错误原因。

Placeholder 不能完全代替 Label。

## 7.3 输入状态

必须支持：

-   Default
-   Hover
-   Focus
-   Filled
-   Disabled
-   Read-only
-   Error
-   Success

## 7.4 校验规则

-   优先在用户完成输入或提交时进行合理校验。
-   错误提示应说明具体问题。
-   错误信息应尽可能靠近对应控件。
-   不应仅通过红色边框表达错误。
-   保留用户已经输入的内容。
-   对异步校验提供加载反馈。

# 8. 弹窗与反馈规范

## 8.1 Dialog

用于需要用户集中注意力处理的任务。

适用场景：

-   删除确认。
-   重要配置。
-   需要明确确认的操作。
-   简短的多步骤交互。

要求：

-   标题清晰。
-   内容简洁。
-   主次按钮明确。
-   避免不必要的多层弹窗。
-   需要确认的危险操作应明确说明影响。

## 8.2 Alert

用于重要的信息提示和决策。

必须区分：

-   Information
-   Warning
-   Error
-   Destructive Confirmation

提示级别应与实际风险一致，避免过度使用警告弹窗。

## 8.3 Toast / Snackbar

用于轻量级操作反馈。

典型场景：

-   保存成功。
-   复制成功。
-   操作失败。
-   网络连接状态变化。

要求：

-   不应阻断用户正常操作。
-   文案简洁。
-   显示时间合理。
-   重要错误不得只通过短暂 Toast 提示。
-   必要时提供撤销或重试入口。

------------------------------------------------------------------------

# 9. 图标规范

## 9.1 基本原则

图标必须具有明确的语义。

-   优先使用统一图标库。
-   相同含义使用相同图标。
-   避免混用多种风格。
-   不使用装饰性图标替代功能图标。
-   重要操作不应仅依靠图标表达。

## 9.2 图标尺寸

建立统一尺寸 Token：

-   12px：辅助标记。
-   16px：紧凑型操作。
-   20px：常规工具栏。
-   24px：主要功能图标。
-   32px：展示型图标。

具体尺寸应根据平台和组件密度调整。

## 9.3 图标按钮

图标按钮必须提供：

-   Tooltip 或可访问名称。
-   Hover 状态。
-   Focus 状态。
-   Disabled 状态。
-   清晰的点击区域。

------------------------------------------------------------------------

# 10. 动效与交互反馈

## 10.1 动效原则

动效必须服务于交互，而不是单纯装饰。

主要用途：

-   表达状态变化。
-   建立空间关系。
-   指示操作结果。
-   引导用户注意力。

## 10.2 动效类型

  类型                使用场景
  ------------------- ----------------------
  Hover               鼠标悬停
  Press               按钮按下
  Transition          状态切换
  Expand / Collapse   内容展开与收起
  Enter / Exit        弹窗及浮层出现和消失
  Loading             数据加载
  Progress            长时间任务进度

## 10.3 动效要求

-   避免过度动画。
-   不允许影响主要操作的响应速度。
-   重要状态变化必须及时反馈。
-   支持减少动态效果的系统设置。
-   长时间任务应提供进度或状态信息。

------------------------------------------------------------------------

# 11. 可访问性规范

所有产品必须考虑可访问性。

基本要求：

1.  交互组件必须支持键盘操作。
2.  必须具有明确的键盘焦点状态。
3.  颜色对比度符合 WCAG 2.2 AA 基础要求。
4.  正常文本对比度至少为 4.5:1。
5.  大字号文本对比度至少为 3:1。
6.  重要图标与界面元素需要足够的对比度。
7.  不能仅通过颜色表达状态。
8.  图标按钮必须提供可访问名称。
9.  表单错误信息应能被辅助技术识别。
10. 支持系统字体缩放及减少动态效果的需求。

------------------------------------------------------------------------

# 12. 响应式与跨平台规范

## 12.1 平台适配

统一设计语言不意味着所有平台必须使用完全相同的交互方式。

应遵循：

-   共享设计原则。
-   共享语义 Token。
-   共享基础组件定义。
-   保留平台原生交互习惯。
-   根据设备输入方式调整控件行为。

例如：

  交互         Windows / macOS   iOS / Android
  ------------ ----------------- ----------------------
  Hover        支持              通常不适用
  右键菜单     支持              以长按等方式替代
  键盘快捷键   支持              根据外接键盘情况支持
  触控反馈     可选              重点支持
  系统导航     遵循桌面习惯      遵循移动平台习惯

## 12.2 响应式布局

根据实际内容和可用空间进行布局调整。

重点考虑：

-   导航区域是否折叠。
-   多列布局是否转为单列。
-   侧边栏是否转换为抽屉。
-   工具栏是否需要收纳次级操作。
-   内容区域是否需要滚动。
-   弹窗是否需要转换为全屏页面。

不得仅通过缩小所有组件来适配小屏幕。

# 13. 多产品设计与组件复用规范

## 13.1 统一基础层

所有产品必须共享：

-   基础颜色语义。
-   字体体系。
-   间距体系。
-   圆角体系。
-   图标规则。
-   按钮基础组件。
-   输入基础组件。
-   反馈组件。

## 13.2 产品扩展层

允许不同产品根据业务特点扩展：

-   业务专用组件。
-   复杂数据展示。
-   特殊工作流。
-   特殊交互模式。
-   产品品牌主题。

扩展组件必须遵循基础组件的状态和交互规范。

## 13.3 组件复用原则

当两个产品出现相同业务语义的组件时，应优先考虑复用。

以下情况允许独立实现：

-   交互语义不同。
-   平台原生行为不同。
-   业务需求存在实质差异。
-   性能或技术约束不允许复用。

不允许仅仅因为视觉效果不同就创建重复组件。

# 14. 设计交付与工程实施规范

## 14.1 Figma 交付要求

设计文件必须包含：

1.  Foundations 页面。
2.  Design Tokens 页面。
3.  Components 页面。
4.  Patterns 页面。
5.  Product Screens 页面。

组件必须使用合理的命名和分组。

推荐命名：

-   Button / Primary
-   Button / Secondary
-   Button / Destructive
-   Input / Default
-   Input / Error
-   Menu / Context
-   Menu / Dropdown
-   Dialog / Confirmation

## 14.2 组件状态交付

交互组件必须交付完整状态：

-   Default
-   Hover
-   Focus
-   Pressed
-   Disabled
-   Loading
-   Selected
-   Error

不允许只交付静态默认状态。

## 14.3 前端实现

设计 Token 应映射到代码变量。

推荐：

-   CSS Variables
-   Theme Provider
-   Component Variants
-   Semantic Tokens
-   Design System Package

所有基础组件必须支持统一的主题管理。

## 14.4 AI 辅助 UI 生成

AI 生成页面时必须遵循：

1.  先识别页面的业务任务。
2.  确定页面信息层级。
3.  选择正确的组件语义。
4.  使用已有设计 Token。
5.  使用已有组件库。
6.  定义交互状态。
7.  检查页面一致性。
8.  检查可访问性。

禁止：

-   随意创造新的颜色和圆角。
-   将菜单、下拉框和选择器混为一谈。
-   在一个区域堆积多个主按钮。
-   用纯视觉样式替代交互语义。
-   每个页面独立创造一套设计语言。

# 15. UI 设计验收标准

每个页面在交付前必须完成以下检查。

## 页面检查

-   [ ] 页面标题是否清楚？
-   [ ] 核心信息是否突出？
-   [ ] 内容分组是否合理？
-   [ ] 主内容与辅助内容是否区分？
-   [ ] 操作是否靠近对应内容？
-   [ ] 是否存在不必要的装饰？

## 按钮检查

-   [ ] 按钮语义是否明确？
-   [ ] 是否存在多个不必要的主按钮？
-   [ ] 危险操作是否明确区分？
-   [ ] 按钮文案是否清晰？
-   [ ] 是否具有完整交互状态？

## 菜单检查

-   [ ] Menu 与 Select 是否正确区分？
-   [ ] Pop-up Button 与 Pull-down Button 是否正确区分？
-   [ ] 应用级菜单与上下文菜单是否正确区分？
-   [ ] 菜单内容是否与当前上下文匹配？
-   [ ] 是否存在过多菜单嵌套？

## 组件检查

-   [ ] 是否优先复用已有组件？
-   [ ] 是否遵循统一 Token？
-   [ ] 是否支持主题切换？
-   [ ] 是否支持必要的响应式行为？
-   [ ] 是否存在不一致的交互反馈？

## 可访问性检查

-   [ ] 是否支持键盘操作？
-   [ ] 是否具有焦点状态？
-   [ ] 文本对比度是否达标？
-   [ ] 图标是否有可访问名称？
-   [ ] 状态是否不只依赖颜色？

# 17. 规范执行原则

本规范作为多产品统一设计体系的基础文件。

执行时遵循以下优先级：

1.  平台原生规范：遵守操作系统必要的交互习惯和无障碍要求。
2.  本设计规范：统一跨产品的设计原则、语义、Token 和基础组件。
3.  产品业务规范：根据具体业务扩展页面模式和业务组件。
4.  页面局部设计：仅在存在明确业务理由时进行特殊处理。

任何对基础规范的偏离，都应说明原因，并评估对其他产品的一致性影响。

**最终目标：让多个产品拥有统一的设计语言，而不是让多个产品拥有完全相同的页面。**
